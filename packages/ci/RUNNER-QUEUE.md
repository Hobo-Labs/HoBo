# HoBo runner queue troubleshooting

GitHub shows **`queued`** (no steps, no runner name) when no self-hosted runner with the job’s label is online. HoBo CI jobs use **`runs-on: hobo`**. Those runners are **ephemeral JIT** registrations created by the HoBo CI relay when it admits a `workflow_job` webhook—not long-lived machines sitting in the org runner list.

## Symptom

- Workflow runs stay **`queued`** for minutes or hours (for example **HoBo CI Fabric** on a pull request).
- Manual **HoBo runner acceptance** with `jit_only=true` also queues if the relay is not dispatching.

A successful acceptance run on `main` or a feature branch only proves the relay worked **at that time**; org transfer or disabled providers can break dispatch without changing workflow YAML.

### Fork pull requests (untrusted code)

Release workflows (`release-hobo` and related) **skip Docker socket work and secret-backed publish** when `github.event.pull_request.head.repo.fork` is true. A lightweight `fork-policy` job documents the skip; contract/static jobs may still run on `hobo` without pushing images or uploading build artifacts that carry workspace `dist/` trees. Require human approval for fork workflows in GitHub branch protection if your org policy demands it.

## Root cause checklist (operator)

Work through these on **Hobo-Labs/HoBo** after an org/repo transfer:

### 1. GitHub App + webhooks

- HoBo CI GitHub App must be **installed on the Hobo-Labs org** (or updated) with access to **Hobo-Labs/HoBo**.
- App webhooks must target the **ingress front door** HTTPS origin (`workflow_job`, `workflow_run`), not a relay URL baked into the App settings. The front door reads **`.hobo/ci.json` at the event’s config ref** and forwards signed webhooks to the selected environment’s `relayOrigin`.
- For **local dev and agents behind NAT**, set `jobAdmission: "pull"` on the `local` environment (or rely on default pull inference for loopback relays). Run `hobo ci enable` against `.hobo/ci.json`, then **`hobo ci serve --environment local --installation-id <id>`** (or `createGithubJobPoller` in custom hosts) — no public URL on your laptop. `hobo ci serve` runs the same poller as the box worker below, every 15 seconds, for the repository it was started for once the relay holds a connection for it; a polled job goes into the relay's inbox and the relay's own tick admits it, so `hobo-trunk` jobs are admitted the same way as `hobo` ones.
- **Fork pull requests** never choose a contributor-controlled relay: routing uses the **base-branch** config ref and `selection.forkPullRequestEnvironment` when set.
- Webhook deliveries should be **200/202** in the GitHub App settings; repeated **401/503** means wrong secret or ingress/relay down.

See [`packages/ci-gh-actions/ONBOARDING.md`](../ci-gh-actions/ONBOARDING.md) and [`packages/ci-gh-actions/deploy/README.md`](../ci-gh-actions/deploy/README.md).

The `@hobo/ci-gh-actions` Biome lint now keeps engine-inventory lookups assertion-free, uses optional chaining for relay ref-prefix checks, explicitly guards test environments before use, and imports Zod as types only where only `z.infer` and `typeof z.json` are needed.

### 2. Repository connection (policy)

Runners tied to **`tyler-r-kendrick/HoBo` do not follow a transfer** to **Hobo-Labs/HoBo**. Re-run isolated repository onboarding:

- `connectIsolatedRepository` for **`Hobo-Labs/HoBo`** with required acknowledgments (`trustedRepositoryAcknowledged`, `publicRepositoryAcknowledged`, `acceptAllMatchingRepositoryJobs`).
- Provider offer enabled with current budget/observation evidence.

Without an admitted connection for the **current** repository full name, the relay ignores jobs even when webhooks arrive.

### 3. Isolated host (required for most CI here)

Admission sets **`isolatedRequired`** when the repo is **public**, on **`pull_request`**, or when the connection is isolated-only. That path needs an **isolated JIT host** on the relay—not the standalone Docker relay’s bridge-only mode.

**Paid path:** Vercel Sandbox (`provider: vercel`, `backend: sandbox`) on the hosted relay.

**Free path (budget exhausted):** add a zero-price **`hobo-box-worker`** offer with **`backend: isolated-container`** and `runsOn: hobo-isolated-worker` (see [`packages/ci/data-models/fixtures/valid/isolated-container-offer.json`](../ci/data-models/fixtures/valid/isolated-container-offer.json)). The legacy provider id `kubernetes` is still accepted for the same backend. Routing picks it when Sandbox reservation would exceed **`offer.budgetMicros`**. Launch requires the **isolated worker sidecar** on an operator-owned VM with Docker.

**Box mode (default): local SQLite + GitHub job poller.** The daemon keeps its own lease journal and webhook inbox in a SQLite file (`node:sqlite`, `@hobo/ci/sqlite`) under the user data dir — **`${XDG_DATA_HOME:-~/.local/share}/hobo-ci/worker.sqlite`**, override with **`HOBO_CI_WORKER_DB`**, never inside the checkout. With SQLite, admission defaults to **pull**: every **`HOBO_CI_JOB_POLL_MS`** (default 5000; minimum 5000) it lists queued and in-progress workflow runs for each connection's repository with the App installation token, keeps jobs whose only label is **`hobo`** or **`hobo-trunk`**, and enqueues a synthetic `workflow_job` delivery into the local inbox. A separate inbox drain pass (default every **≤5s**, budget **30s**, **5s** per delivery via **`HOBO_CI_INBOX_DRAIN_BUDGET_MS`** / **`HOBO_CI_INBOX_DELIVERY_TIMEOUT_MS`**) processes queued deliveries like signed webhooks, including the REST re-check of run and job; the admission tick only reconciles leases and dispatches so poll loops stay under slow-tick alerting. No Vercel relay, webhook ingress, or shared database is needed. The poller pauses on GitHub rate limits (429, 403 with `x-ratelimit-remaining: 0`, or fewer than 300 calls left) until the reset time. To stay well above that floor, every list read—queued, in-progress, newest and completed runs, plus every per-run job list—uses `If-None-Match` with the last ETag whenever one was returned (a 304 does not count against the installation's primary rate limit), rounds the completed-runs lookback down to 10 minutes so that URL holds still, and reads a completed run attempt's jobs only until it has seen all of them completed: a re-run is a new attempt and is read again. An idle poll then costs no rate limit; before, every poll re-read the jobs of each run completed in the last two hours (any workflow, up to 50). Because GitHub's status-filtered list has missed a queued run for over 16 minutes, each poll also reads the newest 50 runs with no status filter (same ETag rule) and unions them with the filtered lists. A refused GitHub read logs `hobo_ci_isolated_worker_github_read_failed` (path and status). `hobo_ci_isolated_worker_jobs_polled` is logged when a poll accepts or refuses a job, fails a read or pauses, and when its `waiting` queued `hobo` jobs (`run/job:result`, not newly accepted) change, then once a minute while they keep waiting. A duplicate queued poll delivery is checked against local pending demand and active leases; uncovered jobs are re-admitted through the relay at most once per minute per delivery id. When a poll's GitHub reads already show a run or job cancelled or completed, admission (at most every 30s) drops matching local pending jobs and unlaunched reservations, clears poll coalesce backoff, and logs `hobo_ci_held_job_pruned` without calling GitHub to cancel or rerun ([finding 113](../../docs/ci/findings/0113-held-jobs-survive-cancelled-runs.md)).

```sh
export HOBO_CI_CONFIG=/etc/hobo-ci/config.json   # or HOBO_CI_CONFIG_JSON; offers + connections, no secrets
export HOBO_CI_GITHUB_APP_ID=…
export HOBO_CI_GITHUB_APP_KEY_FILE=/etc/hobo-ci/app.pem
export HOBO_CI_WORKER_PROVIDER_ACCOUNT_ID=box     # = offer.providerAccountId
node --import tsx packages/ci-gh-actions/scripts/isolated-worker-daemon.mts
```

The daemon imports `@hobo/ci-gh-actions` and `@hobo/ci` from their built `dist`, so the start script first runs `pnpm exec turbo run build --filter=@hobo/ci-gh-actions` (a cache hit on a current tree, about 0.3 s) and refuses to start when that fails, logging `hobo_ci_isolated_worker_start_failed`. Before this, a checkout pulled past a new export started the daemon against the old `dist` and it crashed on a missing export (`createJobDurations` after #1663). Set `HOBO_CI_WORKER_BUILD=0` to skip the build when you build separately; a stale `dist` is then still reported with the rebuild command instead of a bare `SyntaxError`.

On start the daemon applies the config to the journal when it changed (a change refused because an active lease pins the provider identity keeps the stored policy and logs `hobo_ci_isolated_worker_configuration_kept`), and logs one `hobo_ci_isolated_worker_offer` line per offer with `launchable`, `enabled`, `concurrency`, `validUntil`, and `expired`. An expired `validUntil`, or one closer than `maxRuntimeMinutes + startupMinutes`, makes routing skip the offer.

The journal is always SQLite: `HOBO_CI_STORE` may only be `sqlite`, and the shared Postgres partition mode was removed with the hosted relay's database ([ADR-0179](../../docs/design/adr/hosted-relay-stateless.md#adr-0179)). `HOBO_CI_JOB_ADMISSION=push` makes the worker wait for a relay to feed its inbox instead of polling. `hobo ci serve --with-worker` reads the store from the CI project config, `"store": { "kind": "sqlite" }` (the default, at `<HOBO_HOME>/ci/serve/worker.sqlite`). The contract suite (`packages/ci-gh-actions/test/ci-store-contract.test.ts`) runs against that store.

Each job runs in a **fresh Docker container** with the official Actions runner JIT (`labels: [hobo]` or `labels: [hobo-trunk]`, matching the job). The container image is **hermetic**: OS + system packages + pinned Actions runner bundle in a digest-pinned base, then **one OCI layer per tool** from repo-root `mise.toml` / `mise.lock` via **`mise --locked oci build`** (experimental). Healthy jobs do not install Node, pnpm, cue, turbo, gitleaks, shellcheck, syft, or other pinned tools at runtime. As a compatibility path for an older image, preflight discovers missing checkout tools and installs only those with `mise install --locked`, logs the names and elapsed time, then reruns the contract. Whether or not anything was missing, it then resolves each `mise.toml` tool that `command -v` cannot already see with `mise which`, verifies that absolute executable, prepends its bin directory to the current process `PATH`, and appends those dirs to `$GITHUB_PATH` on GitHub Actions so `command -v` probes (for example `syft` on an image predating the syft layer) succeed after a shell-level `mise install`; tools already visible keep their existing resolution and are not resolved again.

### Rebuild the runner image (box worker)

`build.sh` reads tool pins from the checkout only (`MISE_IGNORED_CONFIG_PATHS=/etc/mise/config.toml`). The job container it runs in carries the pins of whichever commit last built `hobo-ci-worker:local`; without this, a pull request that pinned a new tool and rebuilt the image made `mise install --locked` fail on every other branch with `<tool> is not in the lockfile` (release run 42741596338, after an image built with `syft` pinned).

Run on a **native-arch Linux** host (arm64 box builds arm64 only; amd64 builds amd64 — no cross-compile). Requires **Docker** and pinned **mise** (`packages/ci-gh-actions/deploy/ci-runner/mise-version.txt`). Set **`MISE_EXPERIMENTAL=1`** only for the build (the build script exports it).

```sh
# From repo root — exact command Tyler asked for:
bash packages/ci-gh-actions/deploy/ci-runner/build.sh
```

That script:

1. Checks that Docker Hub serves the pinned **`debian:bookworm-slim@sha256:…`** digest (`scripts/ci-runner-verify-base-digest.mts`, anonymous registry API; `docker manifest inspect` from the image's Debian `docker.io` CLI rejects that OCI index) and that `skopeo` is on `PATH` or the engine loads OCI layouts (API ≥ 1.44), then `docker build` with context **`packages/ci-gh-actions/deploy/ci-runner/`** (not repo root) → `hobo-ci-runner-base:local`.
2. Push the base to the local **`registry:2`** container **`hobo-ci-registry`** (recreated for each build with ephemeral tmpfs storage, published on a free `127.0.0.1` port so it cannot collide with anything already on 5000) so `mise oci build --from` does not pull from Docker Hub. The daemon pushes over the published loopback port; inside a job container the script reads the registry at its bridge address. The registry, its transient tags, the OCI layout and any temporary archive are removed after the load.
3. `mise install --locked` + **`mise --locked oci build`** — every configured tool layer from **`mise.lock`**; **`skopeo copy`** loads it as `hobo-ci-worker:<version>`. Without skopeo, `mise oci push --image-dir` puts the layout in the local registry and the daemon `docker pull`s it, because the classic image store's `docker load` reads only docker-save archives. The runner contract runs inside that candidate (inputs streamed in, no bind mount) before it is tagged `:local`.

Version tag: `node --no-warnings scripts/ci-runner-image-version.mts` (hash of `mise.lock`, `mise.toml`, base Dockerfile, `system-packages.txt`, and `build.sh` itself). When `hobo-ci-worker:<version>` is already on the host (a re-run, or main after the pull request that built the same inputs), `build.sh` skips the build: it runs the contract in that image and retags `:local`. On a local miss it next tries `ghcr.io/<owner>/<repo>/hobo-ci-worker:<version>` (lowercased `GITHUB_REPOSITORY`, default `Hobo-Labs/HoBo`), then runs that same contract before promotion. Only a registry miss, unavailable or failed login, or failed contract triggers the native build. The image and release workflows all call this script instead of treating an arbitrary existing `:local` as current. The monolithic fallback uses the same content tag and skip check. Every success prunes BuildKit to the hard cap and deletes unused worker tags other than the current and previous keys; `:local` and every tag of an image used by a running container are protected.

**When to rebuild:** any change to `mise.toml`, `mise.lock`, `packages/ci-gh-actions/deploy/ci-runner/**`, or runner contract scripts. HoBo CI Fabric job **`CI runner image (mise oci)`** rebuilds affected-only on `hobo` when those paths change (needs host Docker socket — worker daemon mounts `/var/run/docker.sock` by default; set `HOBO_CI_MOUNT_DOCKER_SOCKET=0` to disable). On push, the job-level condition checks every commit's added, modified and removed file lists and skips the job when none contains an image input; missing file lists and forced pushes fail open toward building. A skipped job satisfies `needs` immediately, so Main full gate does not wait for a no-op. Inside a job container `build.sh` reaches the registry by the `hobo-ci-registry` container's bridge address (`127.0.0.1` there is the container's own loopback) and loads the layout with `docker load` when the image has no `skopeo`. When the job runs, its Detect step diffs `HEAD~1..HEAD` on a depth-2 checkout (the previous main commit on push, the base on a pull request's merge commit) with `grep`. It is skipped on `merge_group`, so a queue entry never retags `hobo-ci-worker:local` from an unmerged group commit; a pull request that changes the image inputs does retag it, but only after the runner contract passes inside the candidate. GHCR publishing runs on main only. `PR impact gate` and `Main full gate` declare `needs: ci-runner-image` (with `!cancelled()`), so a run that changes the image inputs starts its gate on the image it just built.

**Host disk between jobs.** Each job's Actions work folder is `HOBO_CI_WORKER_WORK_ROOT/hobo-<lease-id>`, bind-mounted into its container. On pass, failure, cancellation, crash or timeout, lifecycle teardown atomically renames it to `HOBO_CI_WORKER_WORK_ROOT/.retired/<lease>-<timestamp>` and triggers a single-flight background sweeper; the original path is free without waiting for recursive deletion. Startup reaps leftovers with the same inactive-lease and absent-container checks, then retires them too. Reaping lists work directories before reading leases afresh, protects every listed directory with an active lease even before its container exists, and retires nothing if that lease read fails. Startup and scheduled GC also trigger the sweeper. Drain-mode shutdown awaits it; handoff mode does not, because the successor's startup sweep finishes the work. `hobo_ci_work_dir_retired` logs the fast handoff and `hobo_ci_work_dir_removed` logs path, bytes, entries and elapsed deletion time; failures log `hobo_ci_work_dir_remove_failed`. Ticks over five seconds log `hobo_ci_isolated_worker_tick_slow` with delivery, worker/lease reconciliation and dispatch timings plus lease and pending counts. `/tmp` still lives in the `--rm` container. `ci-runner-preflight` also prunes untagged images over a day old and stopped `hobo.ci/isolated=1` containers over ten minutes old, then prints `docker system df`; unlabelled containers are never touched.

**Launch failure loop guard.** Every failed launch logs `hobo_ci_launch_failed` with its stage and job identity. Three failures for the same job attempt within 30 minutes cancel the lease, remove its work directory, log `hobo_ci_launch_parked`, and suppress replacement admission for 10 minutes unless the GitHub job state changes first. This prevents a persistent Docker or registration failure from repeatedly creating and deleting multi-GB, inode-heavy work directories. See [finding 64](../../docs/ci/findings/0064-containerless-launch-failures-thrashed-worker-leases.md).

**Workdir inode measurement.** On retire the worker logs **`hobo_ci_work_dir_inode_breakdown`** (`git`, `linkedNodeModules`, `pnpmVirtualStoreInWork`, `other`). Storage peaks learn **`localInodes`** — total workdir entries minus symlinked deps roots and an in-tree **`.pnpm`** virtual store — so the shared store and **`/opt/hobo-deps`** layer do not inflate admission. **`deps-layer.mts link`** collapses stray real **`packages/**/node_modules`** trees back to payload symlinks after a miss **`pnpm install`**. See [finding 105](../../docs/ci/findings/0105-per-job-workdir-inodes.md).

**Shared packages and daemon GC.** Every job mounts the host pnpm store read-write at `/pnpm-store` and installs with `npm_config_package_import_method=hardlink`. The store and work root must be on one filesystem; daemon startup refuses a cross-filesystem configuration. Only scheduled daemon GC requests pnpm pruning; jobs and admission-pressure maintenance never do. A prune requires no active leases and no running container mounting the store, with Docker failure treated as busy. Per-daemon single-flight plus the cross-process `pnpm-store-prune.lock` beside the store prevent concurrent prunes. `pnpm-store-prune.stamp` persists each prune start before spawn and enforces the default **6-hour** interval across failures and restarts; `HOBO_CI_PNPM_STORE_PRUNE_INTERVAL_MS` overrides it with an integer of at least **60000**. The detached prune's entire process group is killed on timeout. Admission waits while pruning and logs `hobo_ci_storage_admission_wait` once with `message=pnpm store prune in progress`; non-rate-limited outcomes log `hobo_ci_pnpm_store_prune` with `{result, ms}`. At least every five minutes and on storage pressure the daemon removes unused `hobo-ci-deps-fetch:*` intermediates, all but the two newest non-local `hobo-ci-deps:*` images, unused worker versions other than the current and previous keys, dangling images, and BuildKit entries beyond the hard 4 GB default cap regardless of age. Both `:local` tags and images used by running containers stay. The cold dev loop job installs only what its script imports (2.2 GB streamed into the offline container instead of 4.6 GB).

**GHCR (optional, public repos):** when `GITHUB_TOKEN` is non-empty, the build logs in and can reuse or push `ghcr.io/<owner>/<repo>/hobo-ci-worker:<version>`. The optional push step runs `scripts/ci/push-ci-runner-image-ghcr.mts`, which retags `:local`, pulls, or rebuilds on the runner executing the push and skips with a notice when the image is still missing (fleet routing may place the step on a different box than the build). With no token, pull and push are skipped and no interactive login is attempted. A failed login also skips the pull and falls back to the native build.

**Deps layer:** `CI deps layer (pnpm)` builds `hobo-ci-deps:<toolchain>-<depsKey>` from the staged lockfile, workspace and dependency-field manifest data, optional npm/pnpm configuration, patches, platform, toolchain version, and an explicit deps-layout version. Layout recipe edits do not change the key unless that version is deliberately bumped; the job-side link/check script is staged into the deps context so mount verify can run `link`, but it is not hashed into the key. Node and pnpm mise entries are already covered by the toolchain version. The build verifies an offline up-to-date install, then proves the candidate under a real uid-1000 job-directory mount before promoting `hobo-ci-deps:local`. Fetch and install reuse the persistent host pnpm store through BuildKit's `hobo-pnpm-store` cache mount. The final image holds repo-relative `node_modules` trees and a key marker under `/opt/hobo-deps`, with no `.git` or files under `_hobo_work`. `scripts/ci/deps-layer-buckets.mts` partitions `.pnpm` entries into 64 reproducible `COPY --link` layers plus one residual layer. Every event first compares the computed key with the `hobo.ci.deps-key` label on `hobo-ci-deps:local`; an exact match skips resolution, verification, promotion, and build. After a read-only GHCR login, a miss checks the exact keyed local tag and then GHCR, skipping the build on either hit; a remaining non-PR miss defers to the publisher and daemon ensure loop instead of rebuilding on Fabric. A PR or publisher rebuild samples free inodes and bytes on Docker's data root before `pnpm install`/`mv` into `/opt/hobo-deps`; below **400000** inodes (`HOBO_CI_DEPS_BUILD_INODE_HEADROOM`) or **8 GiB** (`HOBO_CI_DEPS_BUILD_BYTE_HEADROOM`) it prunes only the BuildKit cache and refuses the rebuild if still short, so a key miss cannot `ENOSPC` main. Never `docker image prune -af`. See [finding 71](../../docs/ci/findings/0071-a-deps-key-miss-rebuilt-without-inode-headroom.md). PRs touching deps-build inputs run with `--no-promote` and never push. Neither Main full gate nor PR impact gate depends on this job. **CI deps image publisher** is a separate `workflow_run`/`workflow_dispatch` workflow that builds the key if no local candidate exists before pushing it; its failure never changes the fabric run's result.

The worker selects the deps image only when the lease repository matches **`HOBO_CI_DEPS_REPOSITORY`** case-insensitively (default **`Hobo-Labs/HoBo`**), **`HOBO_CI_DEPS_IMAGE`** (default **`hobo-ci-deps:local`**) exists, and its `hobo.ci.toolchain` label equals the `hobo-ci-worker:<version>` tag on the current worker image. A once-per-image-id probe checks payload readability and runner-directory writability; failure logs `hobo_ci_deps_image_fallback` with `reason=unwritable-workdir` and falls back. `prepareJobDirectory` creates and chowns the job root, `HoBo`, and `HoBo/HoBo` to uid/gid 1000 so `actions/checkout` can write `.git` inside the bind mount. After checkout, `scripts/ci/deps-layer.mts link` links `/opt/hobo-deps` into the checkout, including for mounted jobs. It links only into package directories the checkout has: a layer built before a package left the tree would otherwise bring that package's directory back holding nothing but `node_modules`, which failed the package-layout check on the first pull request after `packages/code` was removed. `Check deps layer match` additionally requires payload key metadata, `.modules.yaml`, the virtual store, root/workspace `tsx` resolution, and `pnpm exec`; every miss installs. The worker exports **`HOBO_CI_DEPS_LAYER`** only on successful selection, so mounted jobs claim the layer because the payload remains visible outside their mount. A pre-warmed container is reused only when image and deps key match the lease. Default-path box checkouts use `clean: false`, and exact-match gates verify the ts-autocode links. The daily scheduled Main full gate always installs as the correctness verifier, and other jobs retain their frozen install.

For immediate recovery from an unwritable promoted image, stop the daemon, run **`docker rmi hobo-ci-deps:local`**, and restart. Alternatively set **`HOBO_CI_DEPS_IMAGE=`** (empty) and restart to disable selection and the ensure loop. Setting `HOBO_CI_DEPS_REPOSITORY` to a non-HoBo name also disables HoBo selection. Redeploy the fixed daemon and rebuild the image before re-enabling it.

**Daemon-owned availability:** the worker no longer waits for a workflow event to produce the layer. On startup and every **`HOBO_CI_DEPS_POLL_MS`** (default **300000**, five minutes), it checks the head of its default-branch checkout. **`HOBO_CI_DEPS_ROOT`** overrides the default repository root derived from the daemon module, so the service manager's working directory does not matter. A changed head resolves the same toolchain as `build-deps.sh`: the checkout-computed worker tag when present, otherwise the versioned tag on `hobo-ci-worker:local`. It recomputes the key with that explicit toolchain; an unchanged key does no further Docker work. For a missing key it tries `docker pull ghcr.io/<owner>/<repo>/hobo-ci-deps:<key>`, then falls back to one background `build-deps.sh --no-promote` at a time. Success tags the candidate `hobo-ci-deps:local` and runs the daemon's shared keep-2 selector through `scripts/ci-runner-image-gc.mts`. Builds never block admission or consume a worker slot; they run under `nice`/`ionice` with **`HOBO_CI_DEPS_BUILD_MEMORY_MB`** (default **4096**) passed as Docker's `--memory` limit. `hobo_ci_deps_image_ensure_started` logs the key before work and `hobo_ci_deps_image_ensure` logs `{key, action: hit|pull|build, ms}` after success. A failed key read, pull/build, tag, or GC logs `hobo_ci_deps_image_ensure_failed` and retries with exponential backoff from one minute to 15 minutes, fail-open. Jobs continue using the ordinary worker image until the local tag is ready.

**Preflight:** every `runs-on: hobo` job starts with `.github/actions/ci-runner-preflight` (`scripts/ci-runner-preflight.mts`). Failures mean the worker image is stale — rerun `build.sh` on the box.

**CI fabric contract guard** (HoBo CI Fabric `ci-guard` job): `node --import tsx --test scripts/test/ci-runner-image-contract.test.ts` after install. The file uses `node:test`, like its sibling script contract suites; Vitest cannot discover those suites.

**Fallback:** if a tool cannot be packaged with `mise oci` (asdf backend, broken vfox hooks), use `Dockerfile.monolithic` and document why — see `packages/ci-gh-actions/deploy/ci-runner/README.md`.

```sh
export HOBO_CI_WORKER_IMAGE=hobo-ci-worker:local
node --import tsx packages/ci-gh-actions/scripts/isolated-worker-daemon.mts
```

**Graceful stop:** send **`SIGTERM`** (systemd/Kubernetes preStop). The default **`HOBO_CI_WORKER_STOP_MODE=handoff`** stops admitting work, finishes any in-flight poll or launch tick, releases leases that have no container, closes the store, and exits **`0`** without waiting for running job containers. The next daemon adopts those containers through startup and tick reconciliation, so supervisor restarts are near-immediate and trunk jobs are admitted again within seconds. Set **`HOBO_CI_WORKER_STOP_MODE=drain`** for host maintenance or decommissioning (for example `packages/ci-gh-actions/deploy/restart-worker.sh`, which signals **`SIGTERM`** with drain as the default) to wait until every live lease **and** every still-running `hobo-*` container has finished. While draining, reconciliation does **not** abort a `running`/`dispatched`/`claiming` lease for a missing inventory row, does **not** retire its work directory when the container still exists, and does **not** stop unleased running worker containers. Drain reconciles before every count and exits only when **`drainJobInFlight`** reaches zero: running `hobo-*` containers and leases that actually hold a live container or in-flight launch (bare `reserved` rows without a container do not count). Poll/tick/inbox/gc/orphan work is bounded to **30s** on **`SIGTERM`**, with **`hobo_ci_drain_progress`** while either phase runs (default **`HOBO_CI_WORKER_DRAIN_TIMEOUT_MS=1800000`**, 30 minutes for real jobs; the supervisor's stop timeout must be longer). Reconcile cancels reservations whose GitHub run or job already finished, and **`HOBO_CI_WORKER_DRAIN_NO_CONTAINER_MS`** (default **30s**) drops drain holds for leases that never reach a live container — see [finding 108](../../docs/ci/findings/0108-drain-stale-reservation.md) and [finding 114](../../docs/ci/findings/0114-sigterm-drain-counted-non-job-work.md). Drain closes the store and exits **`0`** when drained or **`1`** on timeout. In **drain** mode only, a second **`SIGTERM`/`SIGINT`** exits immediately when no `hobo-*` container is still running.

**Merge-queue admission (pull mode):** each job poll refreshes GitHub merge-queue positions (`HOBO_CI_MERGE_QUEUE_BRANCH`, default `main`) and admits `merge_group` jobs in queue order by head SHA; queue position overrides run `startedAt` when the snapshot is present. Runs whose head SHA is no longer in the queue are deprioritized but never cancelled. Merge-group cap and memory ignore leases in `stopping`/`stopped` and bare `reserved` rows; JIT empty-exit marks `stopping` before settle so cap and memory free immediately.

Job containers run as **`1000:1000`**; when the host Docker socket is mounted, **`createCliDockerDriver`** adds **`--group-add`** for the socket’s gid so in-container **`docker`** can talk to the engine (see **`cli-docker-driver.ts`**).

Job containers are created with **`--init`**. Their PID 1 is `sleep infinity`, which ignores `SIGTERM`, so without an init every **`docker stop -t 30`** ran its full 30 s while the finished lease still held its slot — and the poll tick reconciles leases serially, so that stop also delayed the next launch. Across 43 post-parallel runs the gap between a slot freeing and the next queued job starting had a median of **48 s** (p90 82 s). The change takes effect only after the box daemon is redeployed.

Force-stop settlement on the box worker **re-queues the reserved job** when GitHub still shows it **`queued`** (for example the ephemeral runner picked up a different workflow job first); the store dedupes pending demand.

**Runner exit frees the slot.** The runner start script sets `umask 022` before `run.sh` so job `mkdirSync` directories are `0755`, not world-writable (the Actions runner default umask is `0000`; OpenSesame refuses a world-writable PATH entry as `opensesame_bin_untrusted`). The JIT runner takes one job and exits, but the container (`sleep infinity`) keeps running. `startRunner` therefore writes **`/tmp/hobo-ci-runner-exited`** once `run.sh` returns, whatever its status. Each tick, reconcile checks for the marker with `docker exec <id> test -e` (30 s timeout; a failed check is retried, never treated as an exit) and stops and settles the lease. A slot no longer waits for the job poll (`HOBO_CI_JOB_POLL_MS`) to report the job completed, and a runner that died without taking a job no longer holds its slot until the lease's maximum runtime. Before stop, remove, work-dir retirement, foreign-runner yield, or orphan-container removal, the worker resolves which job GitHub assigned to `hobo-<leaseId>` via the Actions API (reserved run first, then in-progress workflow runs), adopts `actualJobId` / `originalRunId` when GitHub served a different job, and refuses teardown while that runner still holds an active job. Foreign-runner webhook yield retains the lease whenever that adoption still reports an active assignment (including when GitHub served the same job on the box runner but stale REST fields still name another fleet runner). If assignment attribution or the marker is unavailable on a **trunk-labelled** lease, reconcile also reads the original job when `actualJobId` is zero: a completed job whose `runner_name` exactly matches the lease authorizes the same stop on that tick. General leases retain the exact-assignment requirement and incur no additional reads. A swapped lease still checks only its actual job, so the fallback cannot stop a different job using the runner. Settlement requeues the reserved job when GitHub still shows it `queued`. A job can create the marker itself, but that only ends its own container early.

**Memory admission:** exact GitHub job names select `light` (3072 MiB) for guard/lint/contract jobs, `standard` (4096 MiB, the unlisted default), or `heavy` (6144 MiB) for turbo build/test and image lanes. The class remains the Docker `--memory` and `--memory-swap` hard limit and the `HOBO_CI_JOB_MEMORY_MB` value. Before three samples, admission reserves **1024 MiB light**, **2048 MiB standard**, or **4096 MiB heavy**. After three measured peaks for that job name, the last 20 peaks produce `ceil256(max(peak) × 1.25 + 256)`, clamped to 1024 MiB through the class size. An OOM within seven days forces the full class reservation and clears that name's samples. The unmeasured **Main full gate** trunk reservation is therefore 4096 MiB. Active reservations, the standard-sized warm reservation, and the learned trunk reservation must fit the budget. An untouched reservation waiting for a launch slot consumes no container-memory budget. Warm-container reuse compares class limits, not reservations, and the trunk reservation is recomputed on each admission as new peaks arrive.

Every admission and warm-reservation decision also samples `/proc/meminfo` once. The request must leave the configured host reserve (2048 MiB by default) after subtracting its reservation from `MemAvailable`. A blocked job logs `reason=host-available` with `availableMb`; an unavailable or invalid host sample falls back to the budget-only check. With a 13954 MiB budget and a 4096 MiB idle trunk reservation, the PR share is about **9858 MiB**: up to nine light, four standard, or two heavy PR reservations fit before slot and live-host limits. `HOBO_CI_WORKER_MEMORY_LEARN=0` restores full class reservations for every job and trunk. See [finding 24](../../docs/ci/findings/0024-slot-only-admission-let-the-host-oom-killer-choose-a-victim.md) and [finding 62](../../docs/ci/findings/0062-memory-reservations-were-guesses-held-as-hard-limits.md).

Settlement reads the running container's cgroup v2 `memory.peak`, falling back to the v1 maximum-use counter, before stopping it. A readable peak logs `hobo_ci_container_memory_peak` with `jobId`, `jobName`, `memoryClass`, `limitMb`, `reservedMb`, and `peakMb`; measurement failure never blocks settlement. The reserved lease carries `Job.name` as `Lease.jobName` into both peak history and OOM recording. History is stored atomically in `${HOBO_CI_WORKER_WORK_ROOT}/memory-peaks.json` (default `${XDG_STATE_HOME:-~/.local/state}/hobo-ci/work/memory-peaks.json`). Missing or corrupt history starts empty, and `HOBO_CI_WORKER_MEMORY_LEARN=0` restores class-sized reservations without reducing container limits.

**CPU/IO priority and trunk-active PR cap:** rank-0 trunk containers get `--cpu-shares 8192` and request `--blkio-weight 800`; other jobs get 512 and 200 respectively. The 16:1 CPU ratio gives one trunk container about 94.1% of the CPU shared with one PR container on the four-CPU box. IO weighting is optional: the first weighted create/update probes support, and rejection logs `hobo_ci_blkio_weight_unsupported` once and continues with CPU-only weights. Warm spares start at PR weight and are reweighted with `docker update` when assigned. While a trunk lease is active, **`HOBO_CI_WORKER_PR_CAP_WITH_TRUNK`** (default **1**) limits new non-trunk reservations; **0** pauses them. Existing PR jobs are not stopped, the cap disappears when trunk settles, and strict trunk-first ordering is unchanged. See [finding 42](../../docs/ci/performance.md#finding-42-equal-cpu-shares-let-pr-jobs-starve-trunk-tests). These settings take effect only after the box daemon is redeployed.

**Lease/container reconciliation:** at startup, before every admission tick, at drain start and on every drain poll, the daemon lists `docker ps -a --no-trunc --filter label=hobo.ci/isolated=1 --format json` and strictly parses the inventory. A lease with a running, starting or paused container is kept and is never reaped. An exited/dead container is settled through the normal runner-exit/job-completion semantics. Reserved leases are never treated as missing containers. For `dispatching`, `dispatched`, and `claiming` leases, the **two-minute missing-container grace** starts at `dispatchingAt`, not `createdAt`, so time spent waiting for memory does not consume dispatch grace. An in-process in-flight launch also protects its lease and work directory. Once the in-flight tick has finished, drain releases missing-container leases without that wait. Each release logs `hobo_ci_lease_orphan_released` with `leaseId`, `jobId`, `runId`, `state`, `reason`, `ageMs` and `memoryMb`. Admission therefore recomputes memory only from leases that survived the same tick's reconciliation. If launching leases still report memory but there are no worker containers, `hobo_ci_memory_without_containers` records the journal `inUseMb` and lease count.

Running worker containers without an active lease are removed only after the orphan grace **and** when Docker reports `createdAtMs`, the box still holds custody (active lease or GitHub job `queued`/`in_progress` on that runner name), and inventory includes legacy `hobo-*` names without the isolated label. Missing `createdAtMs` never implies age. Containers already in Docker `removing` state and in-flight orphan removals are skipped for the tick (no parallel `docker rm` races). Exited orphans are removed and logged as `hobo_ci_container_orphan_removed`; the protected pre-warmed container is not treated as an orphan. Removal failures log `hobo_ci_container_orphan_remove_failed`. A failed or timed-out Docker listing logs `hobo_ci_lease_reconciliation_failed`, skips the runtime reconciliation/admission pass and releases/removes **nothing** that tick: unknown inventory is never treated as gone, and drain retains conservative in-flight counts until Docker can be read.

**Orphaned GitHub jobs:** candidates identify the job the runner actually ran (`actualJobId`, falling back to the reserved `jobId`), not necessarily the lease's reserved job. Each reconciliation sweeps only this worker's active leases for an actual job assigned to `hobo-<leaseId>` whose container is missing or dead. Exited containers do not enter the sweep: normal exit-marker and exit-code-zero settlements enqueue nothing, while failed nonzero-exit and OOM settlements enqueue through the controller. The sweep reuses the tick's Docker inventory and makes no extra GitHub calls. Its first missing-container or dead-container observation starts the candidate's 60-second confirmation window. Later ticks drop candidates whose jobs completed, returned to `queued`, or moved to another runner. A job still `in_progress` on the same runner is then confirmed orphaned. The worker deletes the runner registration (accepting 204, 404, or the expected busy 422), force-cancels the actual job's run, and waits for it to complete. It then calls `rerun-failed-jobs` once per run attempt for `pull_request` and `push` events. A `merge_group` run is not rerun because its group has already left the merge queue; the log says the pull request needs re-queueing. Other events are not rerun. Candidates are capped at 200, expire after 30 minutes, and remain queued across GitHub 5xx or network failures. Candidate state is in memory. Active leases re-feed the sweep after restart, and controller settlement retains cancelled-lease candidates only in the current process; if that state is lost, GitHub's roughly ten-minute lost-runner timeout remains the fallback.

A feasible rank-0 job waiting for memory, the distinct-merge-group cap, or a slot blocks every lower rank immediately and on later passes until it is admitted. Non-zero ranks retain the HOL backfill window below. A trunk request larger than the whole budget cannot fit even when idle, so it never raises that lower-rank barrier and cannot starve PRs forever. See [finding 36](../../docs/ci/findings/0036-a-waiting-trunk-job-did-not-stop-lower-rank-admission.md).

Wait/admit decisions log `hobo_ci_memory_admission_wait` / `hobo_ci_memory_admitted` with `classMb` and `learned`; Docker-confirmed exit-137 OOM kills log `hobo_ci_container_oom` with the class and job name.

The daemon computes each job's heap from its admitted memory class and injects `NODE_OPTIONS=--max-old-space-size=<heap>` at container creation, so every Node process inherits it and no workflow-level value overrides it. `ci-runner-preflight` also runs `scripts/ci/memory-env.mts` before install (heap math lives in `packages/ci-gh-actions/src/isolated-worker/job-memory-config.ts` so preflight does not load worker peak history). It reads the job cgroup limit and writes the non-blocked **`HOBO_NODE_OPTIONS`** (never `NODE_OPTIONS` through `$GITHUB_ENV`), **`HOBO_TURBO_CONCURRENCY=1`**, and the repo-owned `HOBO_TEST_MAX_WORKERS`. After a 768 MiB native/non-heap allowance, workers are `max(1, min(cpuCount, floor((limit - 768) / 1280) - 1))`; each Node process receives `min(3072, floor((limit - 768) / (workers + 1)))` MiB of heap. Thus `(workers + 1) × heap + 768 <= limit`: the turbo/Vitest parent and every worker fit the same container budget instead of each receiving an independent full-size heap.

**Disk and inode admission:** before each reservation, the daemon samples bytes and inodes on Docker's data root and the work root. Above 85% for either resource it runs the full non-pnpm GC described above at most once per 60 seconds, then samples again; decisions within that interval still use a fresh sample. Above 95% after pruning, the job waits and `hobo_ci_inode_pressure` is logged once per episode. A dispatch pass stops calling storage admission after its first refusal because pressure is host-wide. A trunk-label storage refusal blocks lower ranks and records `hobo_ci_trunk_wait` with `reason: "storage"`. Each admitted job reserves **bytes and inodes** from a **storage class** (`default`, `release_trunk` for Pages/npm/GHCR publish, `runner_image` for OCI gate builds); learned peaks from retired workdirs blend with class caps like memory admission. Defaults without peaks: **200000** workdir plus **170000** container inodes and class byte caps (release trunk **18 GiB** workroot + **6 GiB** container growth). Reservations on the same device add together; consumption since the oldest live grant reduces the outstanding estimate. If free space or inodes minus outstanding growth cannot fit the new job, the same rate-limited GC/recheck runs before the daemon waits and logs `hobo_ci_disk_reserve_wait` or `hobo_ci_inode_reserve_wait` once per episode. Grants without an active lease expire after a 60-second grace, and failed lease reservations release immediately. A live job's directory is never retired or deleted. See [finding 25](../../docs/ci/findings/0025-inode-exhaustion-made-pr-installs-fail-with-enospc.md), [finding 58](../../docs/ci/findings/0058-two-concurrent-jobs-exhausted-inodes-mid-run.md), [finding 68](../../docs/ci/findings/0068-finished-jobs-held-trunk-slots-while-their-work-dirs-were-deleted.md), and [finding 90](../../docs/ci/findings/0090-release-enospc-byte-admission.md).

**Relay mesh:** with `HOBO_CI_NATS_URL` set and pull admission, several workers share one queue with no central relay ([design](../../docs/design/ci-relay-mesh.md)). Each worker advertises its free slots every 10 s and, before it takes a queued job from a poll, asks whether it is its turn. Startup logs `hobo_ci_mesh` with whether it is on.

- **Who takes a job.** Workers rank themselves by how many copies of that job they could start, the same way everywhere: a worker with a free slot but too little free memory for the job is not a candidate for it, and logs `hobo_ci_mesh_job_unfit` with what it lacks. The first-ranked worker claims the job in NATS at once; each later rank waits one step (`HOBO_CI_MESH_STEP_MS`) and claims only if the job is still queued. The claim is an atomic put-if-absent, so one worker wins. `hobo_ci_mesh_job_taken` records the job, the rank and the reason.
- **A worker that is full or draining** advertises no free slots and drops out of the ranking; a drain says so immediately.
- **A worker that dies** stops advertising and is forgotten after a minute. Jobs it was first for start one step later on the next worker. A claim it held ages out after two minutes.
- **NATS down or unreachable** never stops the queue. The worker logs `hobo_ci_mesh_claims_unreachable` and takes its turn by ranking alone on the last view it had; when that view expires it takes everything, as a single worker does. The cost is that two workers can start a runner for one job; GitHub gives the job to one and the other runner exits.
- **Startup does not wait for NATS.** The connection is made in the background and re-made for the life of the process (`hobo_ci_mesh_nats` logs each change).

Jobs waiting for another worker's turn show in `hobo_ci_isolated_worker_jobs_polled` as `mesh-deferred`.

**Reliability.** Each worker advertises the share of its recent jobs it delivered, and its place in the ranking is its capacity for the job times that share: a worker that has been dropping jobs is first for fewer.

- **Delivered:** one of its runners picked the job up, whatever the job's result.
- **Dropped:** the job is still queued ten minutes after the worker claimed it (`never-started`), the launch was given up (`launch-failed`), the container was killed for memory (`out-of-memory`), or the runner was lost mid-job (`runner-lost`). `hobo_ci_mesh_job_dropped` logs each with its reason and the score it left.
- **Not counted:** a job that was cancelled or started elsewhere, and any job the worker did not claim.
- **Recovery:** the record halves every `HOBO_CI_MESH_RELIABILITY_HALF_LIFE_MS`, so a worker that stops dropping jobs is trusted again without anyone resetting it, and sooner if it delivers jobs meanwhile. After ten drops in a row it is ranked with 0.29 of its capacity; an hour after the cause is fixed, 0.62 with nothing delivered; six hours, above 0.99. It never falls below 0.05, so it always gets enough work to prove itself.
- **Across restarts:** the record is kept in the worker's SQLite journal and read back at start, decayed for the time the worker was down (`hobo_ci_mesh` logs `reliabilityRestored`). A restart no longer clears it. After a repair, set `HOBO_CI_MESH_RELIABILITY_RESET` to a new token; it applies once (`hobo_ci_mesh` logs `reliabilityReset`). `hobo_ci_mesh_reliability` logs the score each time it moves a twentieth.
- **What is advertised:** the score, the decayed counts of delivered and dropped jobs behind it, and measured free disk on the work root beside free memory.

**Capacity and availability.** On the same 10-second beat each worker reads the board and reports what changed: `hobo_ci_mesh_node_joined`, `hobo_ci_mesh_node_lost` (an advertisement aged out), `hobo_ci_mesh_node_unhealthy` and `hobo_ci_mesh_node_recovered`, `hobo_ci_mesh_capacity_exhausted` and `hobo_ci_mesh_capacity_restored` (no healthy worker has a free slot), and `hobo_ci_mesh_capacity` with live, healthy and available workers and total and free slots, on every change and once a minute. Only the live worker with the lowest id reports about the others, so each fact appears once.

**Identity and trust.** On first start the worker makes an Ed25519 key (`HOBO_CI_MESH_KEY_FILE`) and signs every advertisement with it; `hobo_ci_mesh` logs its `publicKey`. Each reader computes how far it trusts a node: `trusted` when the key is listed for its node id, `unverified` when it is not listed (or the node does not sign), `invalid` when the signature fails, when the id is bound to a different key, or when the advertisement asks to be believed more than six minutes ahead. An `invalid` advertisement is never ranked and is logged once as `hobo_ci_mesh_node_invalid`. The key's directory must not be group- or world-writable, and a key others can read is tightened to `0600` or refused.

- **The trusted set** lives in the mesh (`trust` in `<namespace>-mesh-config`). With none, each node trusts only itself and ranking is as it was before signatures. Manage it with `pnpm --filter @hobo/ci-gh-actions run mesh:trust list|add <key> --node <id>|remove <key>|require on|off`; nodes pick a change up within 10 s (`hobo_ci_mesh_trust_changed`). Bind every key to its node id: once an id is bound, an advertisement under it with another key is `invalid`. `add <key> --any-node` trusts a key under every unbound id; never use it for a local runner's key, which jobs on that machine can read.
- **Unreadable settings** are never half-applied. A node keeps the last settings it read; one that has never read any fails closed (trusts only itself, ranks only trusted nodes) and logs `hobo_ci_mesh_trust_unreadable`. A field a newer version added is ignored.
- **`require on`** makes nodes rank only listed keys. List every node's key first: with the requirement on and a node unlisted, the others stop deferring to it.
- **What it proves:** which key wrote an advertisement, for which node id, until when. Not what software the node runs, and not that its figures are true. Whoever can write the mesh's config bucket decides whom it trusts; protect it with NATS permissions. See [the design](../../docs/design/ci-relay-mesh.md#trust-whose-advertisement-is-this).

**Listing the nodes.** A relay host started with `HOBO_CI_NATS_URL` is a node too (no slots; its health is its readiness) and serves the list: `GET /v1/mesh/nodes` with a `policy:read` credential, the MCP tool `list_mesh_nodes` and resource `hobo-ci://mesh/nodes`, and `hobo ci status`. Each node shows its state (`live`, `unhealthy`, `lost`) and since when, free and total slots, memory, disk, reliability and trust; at most 256 per answer (`truncated` says when more exist), and the capacity summary counts fleet workers only. A machine running jobs for one repository is shown in full only to the account that owns that repository; others see it under an opaque id. A relay with no mesh answers `mesh: "not-configured"`.

**Shared configuration.** The mesh keeps one configuration in `<namespace>-mesh-config`. A worker with `HOBO_CI_CONFIG` or `HOBO_CI_CONFIG_JSON` runs its own and publishes it if the mesh has none; if the two differ it logs `hobo_ci_mesh_config_drift` and keeps its own. A worker with neither reads the mesh's at start (`hobo_ci_mesh` logs `configuration: mesh`), so a new box needs only the NATS address and App credentials. Replacing the stored configuration requires naming its current revision.

**No hosted database needed.** A worker with `HOBO_CI_STORE` unset keeps its lease journal in SQLite on the box and polls GitHub itself, so the hosted relay is not in the path from a queued job to a running runner. `HOBO_CI_JOB_ADMISSION=push` puts it back in it; the mesh does not need it.

**Tracing:** with an OTLP endpoint or a trace file set, the daemon exports OpenTelemetry spans (`packages/ci-gh-actions/src/relay-trace.ts`; no SDK, no collector of its own). Startup logs `hobo_ci_trace_export` with what is enabled. Two things become spans:

- **Every GitHub call that changes something**, and every call GitHub refused or never answered: `POST …/actions/runners/generate-jitconfig`, `DELETE …/actions/runners/{runner_id}`, `POST …/actions/runs/{run_id}/force-cancel`, `POST …/actions/runs/{run_id}/rerun-failed-jobs`. Each carries the method, the route with ids replaced, the status, the repository and the run, job and runner ids. Successful reads are left out: the worker polls.
- **Every log event in this document.** An event that names a run joins that run's trace. `hobo_ci_job_pickup` becomes a span over the whole wait with three children: `ci.job.queue` (job created to admitted), `ci.job.container_start` and `ci.job.runner_register`.

A run's trace id is derived from its run id alone, and each job's Turbo trace (`scripts/ci/ci-trace.mts`, uploaded as the `ci-trace-*` artifact) uses the same id. Load both into one backend and a run reads top to bottom: queued, admitted, runner registered, Turbo tasks, runner deleted.

To answer "who cancelled this run?", open the run's trace. The only code that cancels a run is the lost-runner path, and it leaves `hobo_ci_orphan_job_confirmed`, a `DELETE` on the runner and a `POST …/force-cancel` span. A cancelled run with no `force-cancel` span was cancelled by someone else: a newer push, a person, or another tool using a token with `actions: write`.

**Events:** traces and logs are for reading; CloudEvents are for reacting. With `HOBO_CI_EVENTS_URL` set, the daemon also delivers the infrastructure facts among its log events as CloudEvents 1.0, mapped from the platform's event envelope as ADR-0046 prescribes. Each has a past-tense type, for example `ci.RunForceCancelled`, `ci.ContainerOomKilled`, `ci.RunnerLaunchFailed`, `ci.JobPickedUp`, `ci.WorkerDrainStarted` and `ci.HostInodePressureDetected`; the full table is `CI_INFRA_EVENT_TYPES` in `packages/ci-gh-actions/src/cloud-events.ts`. A worker in a relay mesh also emits its capacity and availability: `ci.MeshNodeJoined`, `ci.MeshNodeLost`, `ci.MeshNodeDegraded`, `ci.MeshNodeRecovered`, `ci.MeshCapacityExhausted`, `ci.MeshCapacityRestored` and a periodic `ci.MeshCapacityReported`, and what became of the jobs it took: `ci.MeshJobDropped` with the reason, and `ci.MeshReliabilityChanged` each time its score moves a twentieth. `source` is `hobo://<tenant>/ci-worker/<host>/<start>`, `hoboseq` orders one worker start, and an event about a workflow run carries `hobocorrelationid: github-actions-run:<run id>`. Delivery is the CloudEvents HTTP binding in batched structured mode, best effort: a bounded queue, no retry, and `hobo_ci_events_export_problem` when batches fail. The hosted relay emits `ci.RelayStartFailed`, `ci.RelayRequestFailed`, `ci.WebhookIngestFailed`, `ci.ControlRequestFailed` and `ci.ReadinessCheckFailed` the same way.

No request body, response body, header or query string is recorded; JIT runner configs and tokens travel in those. Spans do carry repository names, run and job ids, runner names and job names, so point the endpoint at a backend that may hold them. A slow or dead endpoint cannot stall the worker: spans queue up to 4096, the oldest are dropped past that, a failed batch is not retried, and `hobo_ci_trace_export_problem` reports the counts at most once a minute. Shutdown waits at most 3 s for the last export.

Legacy path `packages/ci-gh-actions/deploy/worker/Dockerfile` is deprecated; use **`build.sh`** above.

This preserves PR isolation without Sandbox spend.

From [`packages/ci-gh-actions/ONBOARDING.md`](../ci-gh-actions/ONBOARDING.md):

### 4. JIT label contract

- Workflows must use exactly one runner label. On the fleet that is **`hobo`**, or **`hobo-trunk`** for the jobs of `push`, `workflow_dispatch` and `merge_group` runs; a routed job asks for whichever label the route job chose (see "Runner routing" below). The relay rejects jobs with extra runner labels. Each JIT runner registers with the one label its lease's job asked for (`packages/ci-gh-actions/src/runner-labels.ts`).
- Trunk-capable jobs in every enabled box workflow, including `hobo-ci.yml` and `release-hobo.yml`, ask for **`hobo-trunk` by default** through `${{ vars.HOBO_CI_TRUNK_RUNNER != 'false' && contains(fromJSON('["push","workflow_dispatch","merge_group"]'), github.event_name) && 'hobo-trunk' || 'hobo' }}`. This includes **PR impact gate** on `merge_group`; its `pull_request` runs use `hobo`. Setting repository variable **`HOBO_CI_TRUNK_RUNNER=false`** is the kill switch that returns trunk runs to `hobo`; pull-request-only jobs always use `hobo`. PR-only jobs, including Secret scan (trunk events scan history inside Main full gate), request plain `hobo`.
- `scripts/lint-actions.ts` allows only that expression and `runs-on: hobo`. Its **`trunk-label-routing`** rule also fails a push/merge-group/dispatch-capable job on plain `hobo` and a PR-only job on the expression. Other repositories served by the same box must use the expression for their push, merge-group, and manual-dispatch jobs too: event rank alone does not reserve trunk capacity, and a shared-label runner can be assigned to an older PR job.
- A trunk-event job still requesting `hobo` logs **`hobo_ci_trunk_job_on_shared_label`** once per job, with `repository`, `workflow`, `runId`, and `jobId`. Treat that event as a workflow misconfiguration; it remains capped with shared-label demand.
- **Rollout:** the box daemon must run a main at or after **#1678**, which serves `hobo-trunk`. The default trunk slot and label-based capacity fixes also need a daemon redeploy. Until both are deployed, set **`HOBO_CI_TRUNK_RUNNER=false`** on an older box; otherwise trunk jobs would wait for a runner nobody launches.
- Registered JIT runners must match **`hobo-{uuid}`** name pattern (see acceptance workflow).

### 5. Budget and concurrency

The relay acknowledges a signed delivery as **`accepted`** once it is in its inbox; admission happens on the worker tick, on every host. When account/provider budget or concurrency is exhausted the job stays in the pending queue with no lease. Check `GET /v1/accounts/self/leases`, relay logs and the policy API; queued GitHub jobs will not start until a reservation succeeds.

Capacity goes out in admission order, not arrival order: `merge_group`, `push` and `workflow_dispatch` jobs first, then pull-request jobs, then `schedule`, and within each the run that started first. A pending job whose single label is `hobo-trunk` keeps trunk rank even if its run lookup fails; a `hobo` job takes its rank from the run event. The poller primes each run's event and start time from the run lists it already reads, without another GitHub request; a later lookup failure retains that rank. Within a run, the box daemon admits the job expected to take longest first: the median of that job name's last five successful durations, which the job poller learns from the jobs lists it already reads. A job with no history counts as 0, and the job id breaks any remaining tie. The history lives in memory and is re-learned from the two-hour completed-runs lookback after a restart. Reservations and reserved-lease launches both use this order. Deferred reservation applies it to the poller's accepted batch regardless of delivery order, and a swapped job re-enters it with the labels read from GitHub.

**`HOBO_CI_WORKER_MERGE_GROUP_LEASES`** defaults to **1 distinct merge group** and must be a positive integer. The daemon groups active reserved and running leases by the run's **`head_sha`** in the admission cache, falling back to a run-specific key if that metadata is unavailable. Another job from a group that already holds a lease is admitted, still subject to memory, slot, and trunk rules; a different group waits and logs **`hobo_ci_merge_group_cap_wait`** once per job with its **`groupKey`**. Finishing the group's last active lease frees the cap, and a waiting merge group never blocks a push job from taking trunk capacity. Set the repository merge queue's **maximum pull requests to build** to **1** on this 16 GiB box too: that is a repository setting, not code, and limits how many groups GitHub builds in parallel before they reach the worker. See [finding 65](../../docs/ci/findings/0065-merge-group-jobs-serialized-behind-the-release-job.md).

Each runner registration logs one **`hobo_ci_job_pickup`** JSON event per lease with **`jobId`**, **`runId`**, **`runEvent`**, **`label`**, **`admittedAt`**, **`containerStartedAt`**, **`runnerRegisteredAt`**, **`admittedToContainerStartedMs`**, and **`containerStartedToRunnerRegisteredMs`**. When the polled or ingested job supplied its creation time, the record also has **`jobCreatedAt`**, **`jobCreatedToAdmittedMs`**, and total **`pickupMs`**. Unknown metadata is omitted, and these records add no GitHub calls.

**`HOBO_CI_WORKER_TRUNK_SLOTS`** defaults to **1** when **`HOBO_CI_WORKER_SLOTS >= 2`**, otherwise **0** (explicit values remain validated from 0 through `HOBO_CI_WORKER_SLOTS - 1`, with the offer's `concurrency` equal to `HOBO_CI_WORKER_SLOTS`). It sets aside slots whose runners GitHub can assign only to **`hobo-trunk`** jobs. Shared-label runs, including push jobs mistakenly still on `hobo`, hold at most `HOBO_CI_WORKER_SLOTS - HOBO_CI_WORKER_TRUNK_SLOTS` active leases. Strict mode is the default: **`HOBO_CI_WORKER_TRUNK_LEND=1`** lends spare trunk capacity to shared-label jobs while no trunk-label job waits. Once one is pending without a lease, the cap applies. In either mode, a trunk-label job that cannot reserve cancels the newest general lease still in `reserved` with no container, runner, or host run, requeues its job, and retries in the same pass. This also lets trunk demand beyond the reserved slot count reclaim general reservations. Leases with a launched host or running job are never cancelled. An idle pre-warmed container has no lease and does not count against the slot budget; launch renames and reuses it. If GitHub gives a trunk runner to another job, the original queued job becomes pending again and takes the next free slot rather than waiting for the borrowed runner to finish, unless this worker already has an idle registered runner with the same label that GitHub reports as unbusy; that runner takes the original job without fresh demand. This requeue reads the still-queued job directly, independently of the poller's duplicate delivery marker, and launches the replacement with the job's own label. The swapped lease continues the other job untouched, while replacement detection permits only one unswapped active lease for the original job.

The target is for a queued main or merge-group job to be admitted on the **next daemon tick after a slot frees**, normally seconds after the poller discovers it. A second trunk job may take a free general slot immediately, or reclaim an unlaunched PR reservation, ahead of all queued PR work. This trunk-to-general borrowing does not depend on `HOBO_CI_WORKER_TRUNK_LEND`; that setting controls only the opposite direction. **Running PR jobs are never preempted**, because killing one would lose its work and fail its PR check. Label separation keeps GitHub from handing a trunk runner to an older PR job ([finding 13](../../docs/ci/findings/0013-github-gave-the-runner-launched-for-main-to-an-older-pr-job.md)).

A trunk job that cannot reserve for more than **10 s** logs one **`hobo_ci_trunk_wait`** JSON event per wait episode with **`reason: "lease-capacity"`**, **`waitedMs`**, **`repository`**, **`runId`**, and **`jobId`**. Its wait clock survives across relay ticks and resets after reservation or when the job leaves the queue. Use this to separate lease-capacity starvation from job discovery and container startup. The 2026-11-04 incident and completed-original-job reconciliation fallback are recorded in [finding 27](../../docs/ci/findings/0027-a-completed-merge-group-lease-still-occupied-the-trunk-slot.md).

The daemon change and its `HOBO_CI_WORKER_TRUNK_*` settings take effect only after a box redeploy. See [finding 9](../../docs/ci/findings/0009-a-freed-slot-went-to-whichever-job-the-worker-saw-first.md), [finding 11](../../docs/ci/findings/0011-a-runs-long-pole-was-admitted-last.md), [finding 15](../../docs/ci/findings/0015-trunk-jobs-starved-for-16-minutes.md), and [finding 23](../../docs/ci/findings/0023-the-trunk-slot-went-to-a-runner-a-pr-job-could-take.md).

### 6. Optional overflow (Hostinger ARC, GitHub-hosted)

Overflow is off until you enable it. While the hobo fleet has a free slot, jobs stay there. When overflow members are enabled and hobo is full, admission spills to Hostinger ARC (`runsOn: hobo-arc`), then GitHub-hosted (`runsOn: ubuntu-24.04`). Policy rejects `ubuntu-latest`.

`.hobo/ci.json` `environments.ci.policy.providers` ships both disabled:

- `github-hosted`: `kind: github`, `connectionRef: github-hosted`, `runsOn: ubuntu-24.04`, `enabled: false`.
- `hostinger-arc`: `kind: kubernetes`, `connectionRef: hostinger-arc`, `runsOn: hobo-arc`, `enabled: false`, and `scaleSet` with `name`, `namespace`, `minRunners`, and `maxRunners`. The runtime offer uses backend `gh-actions`. `isolated-container` stays paired with `runsOn: hobo-isolated-worker` on the box worker.

Anti-loop: a job already labeled `ubuntu-24.04` or `hobo-arc` stays on that member and is not sent back to hobo. Queued demand for a GitHub-hosted or ARC offer keeps that concrete label instead of `hobo`. Isolated abort covers Vercel Sandbox, `hobo-box-worker`, and kubernetes `isolated-container` on `hobo-isolated-worker`. It does not cancel kubernetes `gh-actions` ARC leases, and it skips kubernetes when the offer backend is unknown.

#### Host health

Memory and storage admission answer for one job at a time. The daemon also watches the machine as a whole and logs **`hobo_ci_host_health`** with `state`, `previous`, `reasons`, `loadPerCpu`, `memoryAvailableFraction`, `storageFreeBytesFraction` and `storageFreeInodesFraction` (the worst of Docker's data root and the work root). It samples at most every 10 s from the dispatch tick.

| State | When (defaults) | What the daemon does |
| --- | --- | --- |
| `ok` | below every threshold | nothing |
| `pressured` | 1-minute load ≥ 1.5 per CPU, available memory ≤ 15%, or free bytes or inodes ≤ 15% | runs storage collection as soon as the current tick ends when the reason is storage, instead of at the next `gcIntervalMs` |
| `critical` | load ≥ 3 per CPU, available memory ≤ 7%, or free bytes or inodes ≤ 5% | also marks the box's offers unhealthy for the fleet route table, so new jobs are routed elsewhere when another member is admitted |

The state rises only after three consecutive samples worse than the held level and falls only after six better than it, so a single spike or a single quiet sample does not move it; a run that moves between two bad levels settles on the milder one. Load is divided by the host's logical CPUs, not the daemon's cgroup share. A sample that takes longer than two seconds counts as unread, so a stalled disk cannot hold up the dispatch tick. A lasting `pressured` or `critical` state is logged again every five minutes; a sample that cannot be read logs **`hobo_ci_host_health_sample_failed`** and leaves the state as it was. A job that was assigned a runner and then failed in **Set up job** with no log, minutes later, is the signature to check this record against: the runner died with the job, and a dead runner's run is force-cancelled and re-run ([finding 63](../../docs/ci/findings/0063-a-dead-runner-left-its-github-job-in-progress.md)).

Host health does not stop admission by itself: memory and storage admission still decide whether a job launches. It changes where the fleet sends work that has not been queued yet, and that only takes effect once a workflow reads the route table.

**PSI, CPU admission, and stall recovery (Linux):** the dispatch tick also logs **`hobo_ci_host_resource_pressure`** about every 10 s with memory/CPU/IO PSI `full` avg10, swap use, and load — separate from per-job `hobo_ci_memory_admitted` and container peaks. Worker memory admission applies **`HOBO_CI_FLEET_CAPACITY_VOLATILITY_MB`** to MemAvailable and refuses with `reason: host-pressure` when PSI or swap thrash crosses fixed thresholds, even if raw `MemAvailable` still looks adequate. CPU pressure is read from PSI `some` (the kernel reports system-wide CPU `full` as zero). The MemAvailable it compares is the lowest reading over **`HOBO_CI_WORKER_MEMORY_LOW_WATER_MS`**, less the reservations of admitted jobs that have not taken their memory yet (**`HOBO_CI_WORKER_MEMORY_RAMP_MS`**; waits log `committedMb`), so jobs admitted seconds apart are not all checked against the same free memory ([finding 142](../../docs/ci/findings/0142-box-admission-counted-neither-promised-memory-nor-lasting-headroom.md)). For **standard-class** trunk jobs (≥ 4096 MiB), admission also reserves **~4 CPUs** per active standard-or-heavier container and compares **logical cores − 1m load − reserved − 1 CPU volatility** against that request; refusal logs **`reason: cpu-contention`** with `cpuHeadroom` fields. A job that has started keeps the share of those CPUs the 1-minute load average does not show yet (`e^(−t/60 s)`, zero after three minutes). **`cpu-contention`** shares the trunk headroom fleet-defer path ([finding 111](../../docs/ci/findings/0111-trunk-headroom-fleet-defer.md)): immediate defer when **`peerAbsorbSlots > 0`**, else defer after **`HOBO_CI_TRUNK_HEADROOM_FLEET_DEFER_MS`**. While a job container is running, consecutive stall samples log **`hobo_ci_container_stall_requeue`** and stop only the local container; **`stall-job-recovery`** may request one per-job `rerun` on main push or merge_group within 15 minutes (pull_request: annotate only; never workflow cancel). See [finding 101](../../docs/ci/findings/0101-shared-box-memory-stall-on-shard-1.md) and [finding 116](../../docs/ci/findings/0116-main-shard-timeout-cpu-admission.md).

**Dead JIT registration:** before reserving demand, the relay refuses a duplicate lease for a job that already has box custody and deregisters a **`hobo-<lease-uuid>`** runner when GitHub shows `in_progress` without a live local lease (`hobo_ci_jit_runner_ghost_binding_cleared`). Isolated settle always deregisters the runner name it registered. See [finding 102](../../docs/ci/findings/0102-dead-jit-runner-shard-two-checkout.md).

**Fleet witness (peer host offline):** the minting host owns deregister when its shared relay lease is still active and the container exits. Any other box worker may act as a **fleet witness** when GitHub reports the assigned peer **`hobo-<lease-uuid>`** runner **offline** — witness release runs before storage/memory admission and on `in_progress` webhooks, never while the peer runner is still `online`, and never for ARC (`hobo-runner-*`) or GitHub-hosted runners. Main-gate witness reruns follow the stall policy (single job `rerun`, no workflow cancel). See [finding 103](../../docs/ci/findings/0103-offline-peer-jit-shard-two.md).

**Main Fabric trunk pickup:** on a shared push run, admission orders **Main workspace plan** before **Main full gate**, then workspace shards by index (`admission-order.ts` `mainFabricTrunkPhase`) for **pending reservation and reserved launch**. When local **`trunkSlots`** are full **or** a trunk job waited on headroom/storage longer than **`HOBO_CI_TRUNK_HEADROOM_FLEET_DEFER_MS`**, and mesh **`arcFreeSlots > 0`**, the relay defers reserving additional **Main workspace test shard** jobs locally (`hobo_ci_trunk_wait` `reason=fleet-capacity`) or requeues unlaunched custody (`hobo_ci_trunk_headroom_fleet_defer`) so ARC or peer box workers claim them. See [finding 107](../../docs/ci/findings/0107-plan-shard-fleet-pickup.md) and [finding 111](../../docs/ci/findings/0111-trunk-headroom-fleet-defer.md).

**Unlaunched reservation release:** when a box worker reserves demand but does not start a container (slot cap, storage, or memory admission), it cooperates with mesh capacity instead of churning custody. After the reserve pass, **`releaseBlockedUnlaunchedReservations`** cancels and requeues only when **`arcFreeSlots` (mesh non-local capacity) > 0** so ARC or a peer box can absorb the job, and either the reservation age exceeds **`HOBO_CI_UNLAUNCHED_RESERVE_MS`** (default 25000) or — when **`HOBO_CI_UNLAUNCHED_BACKLOG_IMMEDIATE`** is not `0` — **pending + unlaunched** exceeds **launch slots minus live containers** after **`HOBO_CI_UNLAUNCHED_BACKLOG_MIN_AGE_MS`** (defaults to the launch bound, not one tick). **`HOBO_CI_UNLAUNCHED_RE_RESERVE_COOLDOWN_MS`** (default 30000) blocks re-reserving the same job until mesh headroom improves. Logs **`hobo_ci_unlaunched_reservation_released`** with **`releaseCount`** and **`nonLocalFreeSlots`**. See [finding 104](../../docs/ci/findings/0104-unlaunched-reservation-custody.md) and [finding 106](../../docs/ci/findings/0106-unlaunched-release-churn.md).

#### Fleet balancing and the route table

The fixed box → ARC → GitHub order above is what admission applies to a job that is already queued. Ahead of the queue, the relay can balance every connected offer through the budget policy and publish which label a new job should ask for; see [CI fleet balancing](../../docs/design/ci-fleet-balancing.md).

- Set **`HOBO_CI_FLEET_ROUTES=1`** on the box daemon (`0` or unset is off; any other value refuses to start). After each dispatch pass it writes the repository variables **`HOBO_CI_FLEET_ROUTES`**, for example `{"fork":"hobo","pr":"ubuntu-24.04","trunk":"hobo-trunk"}`, and **`HOBO_CI_FLEET_CAPACITY`** (live MemAvailable minus reservations and **`HOBO_CI_FLEET_CAPACITY_VOLATILITY_MB`**, default 1024, with `admit` / `freeSlots` per label). The daemon's startup record reports `publishFleetRoutes`.
- The HoBo CI GitHub App needs repository **Variables: write**. Without it a refused write logs **`hobo_ci_fleet_routes_error`** with the HTTP `status` and is not attempted again for ten minutes; admission is unaffected.
- The variable outlives the daemon. A `drain` stop puts every class back on its hobo label (logged with `reset: true`); a `handoff` leaves the table for the successor. **To turn publishing off, delete the variable** (or drain first): a daemon restarted with `HOBO_CI_FLEET_ROUTES=0` does not touch it, and a crash leaves the last table in force.
- A successful write logs **`hobo_ci_fleet_routes_published`** with `repository`, `variable` and `value`. The variable changes only when the table does, and at most once a minute.
- **Route runners** reads **`HOBO_CI_FLEET_CAPACITY`** (when set) with the queue limits so a main run does not choose the fleet when the box cannot admit the job's memory class. Enable publishing on the box before relying on that signal; without it routing falls back to queue heuristics only. As of finding 142 the worker publishes the `version: 1` / `admittedParallel` shape, which this reader does not parse, so the route job logs `fleet capacity unset` and uses queue heuristics.
- Cooperative mesh defer for headroom/storage-blocked trunk jobs uses **`HOBO_CI_TRUNK_HEADROOM_FLEET_DEFER_MS`** (default 45000) and mesh **`arcFreeSlots`**; it does not cancel or rerun workflow runs.
- `.hobo/ci.json` accepts provider kinds **`jog`** and **`boat`** from a relay built at or after this change. Do not add them to the file an older deployed relay reads: an unknown kind fails policy parsing.

### Runner routing: the fleet, then a local box, then GitHub-hosted

A workflow run no longer waits on a fleet that is not taking jobs. Every routed workflow starts with a **Route runners** job on `ubuntu-24.04`, and every other job asks for the label that job chose.

| Tier | Label | Chosen when |
|---|---|---|
| Fleet | `hobo`, or `hobo-trunk` for trunk events | It is taking jobs (below) |
| Local box | `hobo-local-host` | The fleet is not taking jobs, a local box is enrolled, and it is |
| GitHub-hosted | `ubuntu-24.04` | Neither of the above |

- **How availability is read.** From GitHub's queue, which every backend shares, looking only at jobs whose one label is the tier's label. A backend is taking jobs when all four hold: a runner took such a job in the last 15 minutes; no such job has waited 120 seconds; no job it took in the last 15 minutes had waited that long; and fewer than 4 are already waiting. A fleet that is down, full, or cut off from its relay looks the same there, and nothing has to be asked of it. A job queued for more than a day is treated as abandoned and ignored.
- **Why a pickup has to be seen.** The wait alone was the first rule, with a 300 second limit. After a round of cancelled runs emptied the queue, it refilled with eleven jobs, the oldest 283 seconds old, and the next run joined them: a queue that was just emptied is full long before its oldest job is old. The count and the recent-pickup limits fixed that, and then the merge queue was rebuilt, ten runs chose in the same second, each saw nothing waiting for a fleet that was taking minutes to pick a job up, and all ten were sent to it. An empty queue says nothing, so a label is sent work only after a runner has been seen taking a job for it.
- **The probe keeps a pickup on record.** `fleet-probe.yml` has one job per self-hosted label (`hobo`, `hobo-trunk`, and `hobo-local-host` when a box is enrolled), each doing nothing but being picked up. Every **HoBo CI Fabric** run starts one, and nothing runs while the repository is quiet. Each label has its own concurrency group and a probe job waiting for a runner is never cancelled, so a label that is down holds one job that goes on waiting (which reads as refusing after 120 seconds) and at most one behind it, and does not hold up the probe of another label. The probe holds no permissions and `scripts/lint-actions.ts` rejects any step in it but `run: "true"`.
- **A slow pickup is remembered for an hour.** The probe is one small job: a runner taking it at once says the label is alive, not that it can take a run. A run sent to the fleet on that alone waited 17 minutes for runners. So a job that waited past the limit counts against its label for 60 minutes, while a pickup counts for it for 15. To find such jobs after their run has finished, the route job also reads the three finished runs of the last hour that took longest: the run list does not say which runner a run used, but a run a slow backend held up is one that took long. A fleet that cannot keep up is therefore tried by one run in the hour, not by every run that finds it idle.
- **After a quiet spell** nothing has been seen on any label. A run in that position waits up to 60 seconds for the probe its own start set off, looking every 10 seconds, and uses the fleet if a runner picks the probe up. It waits only when the probe could change the answer: the label has no pickup on record, nothing says it is refusing jobs, and a probe is under way.
- **Runs that start together take turns.** Each would read the same queue before any of them had added to it. So while a run that started in the 60 seconds before this one has not finished its route job, this one leaves the self-hosted runners to it and goes to GitHub-hosted. A push that starts five workflows sends the first to the fleet and the rest to GitHub-hosted; the next push reads a queue that has the first one's jobs in it.
- **Limits.** Repository variables **`HOBO_CI_ROUTE_MAX_WAIT_SECONDS`** (120) and **`HOBO_CI_ROUTE_MAX_QUEUED`** (4; the box has two slots, so four waiting is two rounds).
- **The local box.** Set repository variable **`HOBO_CI_LOCAL_RUNNER=true`** once a box is registered under `hobo-local-host` (the `local` provider kind's label, see `packages/ci-gh-actions/LOCAL-DEVELOPMENT.md`). The variable says a box is enrolled, not that it is connected: a box that is enrolled and offline never picks its probe up, so it is never sent work.
- **Pinning.** Repository variable **`HOBO_CI_ROUTE`**: `fleet` restores the behaviour before routing (the kill switch), `github` or `local` sends everything to that tier, and unset or `auto` falls back as above.
- **It cannot fail a run.** If the queue cannot be read, or the script cannot run, GitHub-hosted is chosen: the route job is running there, so it is the one tier known to be up. Pinned to the fleet, the run stays on the fleet. If the route job itself does not succeed, jobs ask for the fleet's label and both required gates fail closed.
- **The decision is made once per run**, when it starts. A run routed to the fleet that then stalls stays there; re-running the workflow routes it again.
- **On a GitHub-hosted machine** the job runs the same steps. `ci-runner-preflight` installs the pinned mise and the tools in `mise.lock` first (`.github/actions/ci-runner-preflight/hosted-toolchain.sh`); the pnpm store and Turbo cache use their `actions/cache` paths; there is no deps layer, so dependencies are installed from the lockfile.
- **Browser tests there** use the same pinned headless shell the image bakes in: jobs that run package tests pass `browser: "true"` to `ci-runner-preflight`, which downloads it to `/opt/pw-browsers` and checks its digest against the image's Dockerfile.
- **One test does not run there:** `storage-admission.test.ts` gives a directory to the image's user (uid 1000), which only that user and root may do. A GitHub-hosted machine runs as another user, so that test is skipped there and runs on the fleet.
- **Container tests run there.** A GitHub-hosted machine has a Docker engine, so the container tests in `@hobo/ci-gh-actions` (the pinned Pact-broker Postgres image among them) run instead of being skipped. They start in separate processes and share one Testcontainers reaper; `test/fixtures/start-container.ts` starts again when a reaper another file left behind is still listed but no longer answering.
- **The one job that differs there** is the cold dev loop. On the fleet it runs in the worker image with the network disabled. An ARC pod (`hobo-runner-*`) has Docker but neither the worker image nor `sudo`, so it first pulls the content-keyed image from GHCR (`ensure-ci-worker-image.mts --materialize-only`, which is why the job holds `packages: read`) and then runs the same way. A GitHub-hosted machine has no worker image but has `sudo`, so it runs the same commands on a copy of the tree in a network namespace whose only interface is loopback. When GHCR has no image for the content key (a PR that changes the runner image's inputs, or a fork PR that may not pull), a runner with no `sudo` builds the image itself (`ensure-ci-worker-image.mts`, build.sh's 600 s budget; the job allows 20 minutes). A runner that can do none of these fails with an `::error` naming why, instead of `sudo: command not found`.
- **A signed local run changes the answer.** When the route job verifies one for the tree it checked out, the jobs it covers are skipped and the rest go to `ubuntu-24.04` without reading the queue. See "Signed local runs" below.
- **Always GitHub-hosted:** the route job, and the two required gates (**PR impact gate**, **HoBo release PR gate**). The gates run no repository code and only add up other jobs' results. On the fleet, a superseded run's gate had to find a runner before the next run could start, which held one pull request for 30 minutes.
- **Not routed:** tag, publish and attest jobs in the release workflows, `ci-deps-publish.yml`, and **CI deps layer (pnpm)** in `hobo-ci.yml`. On a pull request the deps layer job asks for **`hobo-box`**, the box's own label (the worker serves it; no ARC pod does), because it builds the image in the box's Docker context: under the shared `hobo` label an ARC pod could take the job and build several GB that no job container reads. Trunk events keep the trunk label. Set the repository variable **`HOBO_CI_BOX_RUNNER=false`** to fall back to `hobo` if a box daemon does not serve the label. `scripts/lint-actions.ts` requires this expression for any job that runs `deps/build-deps.sh` and allows it for no other. They build or push the fleet's own images. The deps layer job was routed at first; on a GitHub-hosted machine it has no worker image and no box Docker context, and failed before it reached the build for every pull request that touched a deps-image input. Neither gate needs it, so on a slow fleet only that check waits.
- **It does not read `HOBO_CI_FLEET_ROUTES`.** It reads **`HOBO_CI_FLEET_CAPACITY`** when the box publishes it, plus the shared queue, so overflow to GitHub-hosted or ARC happens before jobs park on a label that cannot launch. The route table the relay can publish (above) says what the fleet would choose when the relay is up; this job has to decide when it is not, so it reads the queue.
- **It reads `HOBO_CI_FLEET_STATE` when it is fresh.** Workers with `HOBO_CI_FLEET_ROUTES=1` in a relay mesh also keep that variable: one elected worker (the lowest live id serving a fleet label) writes, per fleet label it serves, the live nodes and their free slots, with when it was published; never `hobo-local-host`. A snapshot five minutes old or less that shows the run's label with no node or no free slot counts as that backend refusing jobs, at once. One that shows room changes nothing (the queue still decides), and so does a missing, unreadable or older one, or one that does not list the label. The worker writes only when a label gains or loses its last node or free slot, otherwise every two minutes, and once as it starts to drain; `hobo_ci_fleet_state_published` (with what routing reads, not the value) and `hobo_ci_fleet_state_error` log the writes. It needs the same `Variables: write` permission as the route table.
- **Where it lives:** `scripts/ci/route-runner.mts` (decision and queue reading), `.github/actions/route-runner` (the step), `.github/workflows/fleet-probe.yml` (the probe), `selectFleetBackend` in `packages/ci/src/fleet-overflow.ts` (the order: fleet, ARC, local box, GitHub-hosted), and `scripts/lint-actions.ts` (which labels a workflow may ask for).

### Signed local runs: CI on your own machine

A pull request's CI jobs can be run on a developer's machine, signed, and published. The workflows then **verify** that record on a GitHub-hosted machine in seconds and skip the jobs it covers. No fleet runner is needed for them, so a fleet that is down or slow does not hold the pull request. With no valid record, every job runs exactly as before.

```bash
git fetch origin && git merge origin/main        # the head must contain the base tip
pnpm ci:attest run                               # runs the covered jobs, signs the result
pnpm ci:attest publish                           # pushes it to the ci-attestations branch
git push                                         # only now: the run that starts finds the record
```

| Step | What it does |
|---|---|
| `pnpm ci:attest init-key` | Creates this machine's ed25519 key at `$HOBO_CI_ATTESTOR_KEY` (default `~/.config/hobo/ci-attestor/ed25519.pem`, directory `0700`, file `0600`) if there is none, and prints only the **public** trust entry. The private key is never printed. |
| `pnpm ci:attest run` | Refuses a dirty tree. Fetches the base (`origin/main`, or `--base=`). Refuses a head that does not contain the base tip and says how to fix it. Runs each covered job's commands and writes the signed record to `.hobo/attestations-out/<tree>.json`, with each job's log beside it. If any command fails, or a command rewrote a tracked file, it exits non-zero and signs nothing. Each step gets an allowlisted environment and a scratch `HOME` (below). `--fresh` makes Turbo run every task again instead of replaying its cache. |
| `pnpm ci:attest publish` | Checks the record first, the way a workflow would, against the keys trusted at the record's own base commit, and pushes nothing that would be refused. It then commits the record as `attestations/<tree>.json` on the orphan branch `ci-attestations` and pushes it. It uses git plumbing in a temporary index and pushes from a scratch bare repository that borrows your checkout's objects, so your checkout, index, HEAD and refs, including remote-tracking refs, are not touched. A push that loses a race is rebuilt on the new tip and retried, five times at most. The remote's URL never appears in its output, and credentials in any URL git reports are masked. |
| `pnpm ci:attest verify` | The same check the workflows make, with git in place of the GitHub API. |

- **What is covered.** In `hobo-ci.yml`: `pr_gate_validation`, `workspace_tests` (every shard), `pr_affected`, `pr-offpath`, `artifact-trust`, `ci-guard`, `secret-scan`. In `release-hobo.yml`: `release-contract`, but only when no release image is affected. If `release-oci-affected.mts` reports an image, the local run leaves that job out of the record and it runs in CI as usual.
- **What is not covered** and still runs in CI: `ci-runner-image`, `ci-deps-image`, `dev-cold-loop-gate`, the route job and both gates. The cold dev loop was considered and left out: its own install step narrows `node_modules` to a few packages, which would break the shared checkout the other jobs run in, and its offline copy of a fully installed tree is several gigabytes.
- **The same commands.** `scripts/ci/attested-jobs.json` holds each covered job's steps as the workflow writes them: the script, the `if:`, the `env:`, in order. The local runner reads only that file, never a workflow. `scripts/test/attested-jobs.test.ts` fails when a workflow job and its description differ in any step. Steps that set up or tidy a CI machine (checkout, preflight, cache restore and save, trace export) are marked `skip` with a reason; every other step runs. When `main` changes a covered job, that test fails on every branch that rebases onto it until the description is updated to match, so a local run never signs for an older version of a job.
- **Both events in one record.** The run executes each job once as `pull_request` and once as `merge_group`, with each step's own condition deciding. So the merge-group-only steps (the two contract tests and the S0 gate set in `pr_gate_validation`) run too, and one record is valid for both events. A command already passed with identical inputs for the same event is not run twice. Each job's result lists the events it ran for, and the verifier accepts a job only for an event in that list. `--events=merge_group` makes a record that covers the merge group's jobs and nothing for the pull request.
- **The tree it is bound to.** GitHub tests a pull request as a merge of its head into the base. That merge has the head's own tree exactly when the head already contains the base tip, which is why `run` requires it. The run rebuilds that merge commit locally (base first, head second, the head's tree) and points `HEAD` at it for the duration, because the jobs read `HEAD^1` and `HEAD^2`. The index and files do not change, and `HEAD` is put back afterwards, also on Ctrl-C.
- **How a workflow verifies.** The **Route runners** job checks out `scripts/ci/verify-attestation.mts` and runs it first. It takes the tree of the commit it checked out, reads the event's base commit (`pull_request.base.sha` or `merge_group.base_sha`) and that commit's tree, reads `.hobo/ci-attestors.json` **at that base commit**, and reads `attestations/<tree>.json` on `ci-attestations`, all through the GitHub API with the job's read-only token. The record is accepted only if the signature verifies with a key listed at the base, that key has not expired, and the record names this tree, this base tree and this event. The list at the base is refused whole if any entry's `id` is not its own key's id, if any `expiresAt` is not strict ISO-8601 UTC, or if any entry expires more than 90 days later. Of the record's jobs, only those that ran for this event are reported. **Secret scan** is reported only when the record's `head` and `base` are exactly the event's `pull_request.head.sha` and base sha: it scans commits, and another history (a secret added, then reverted) can end in the same tree. Every other covered job is bound to the tree. The job then outputs `attested` (`true` or `false`) and `attested-jobs` (a JSON array). What it prints is one line: control characters from an API answer or a record are replaced.
- **It cannot fail a run.** No record, an API error, a bad signature, an expired key, a script that does not start: each is `attested=false`.
- **Skipping.** Each covered job has a condition that skips it when `needs.route.outputs.attested == 'true'` and its own id is in `attested-jobs`. A skipped job needs no runner at all. `scripts/lint-actions.ts` rejects that condition on a job that is not covered, or naming another job's id.
- **The gates.** **PR impact gate** needs the route job and accepts a skipped validation, workspace or affected-lanes job only when the route job succeeded and reported that job attested. A failed or cancelled job never passes, and with no attestation its rules are the old ones. **HoBo release PR gate** requires the route job to have succeeded and now accepts a skipped release contract only when the route job reported it attested; before, it accepted any skipped contract. Both gates decide with the same `attested()` shell helper, and `scripts/lint-actions.ts` rejects a gate that waits on a covered job and does not use it unchanged. **CI fabric contract guard** and **Secret scan** are required by name and are satisfied by being skipped, as they already are on `merge_group`.
- **Routing.** An attested run sends what is left to `ubuntu-24.04` without reading the queue. A pinned `HOBO_CI_ROUTE` still wins, so with `fleet` pinned the uncovered jobs wait for the fleet.
- **Merge groups.** The record matches a merge-group run only when the queue's group commit has the same tree: the pull request is first in the queue and its head already contains the queue's base. Otherwise the tree differs, verification says `attested=false`, and the merge group runs in CI as it does today. Nothing tries to predict a queue tree.
- **Timing.** A run reads the record when it starts. Publish before you push. A record published later is picked up by re-running the workflow.
- **Adding a machine.** Run `pnpm ci:attest init-key --note="whose machine"`, add the printed entry to `.hobo/ci-attestors.json`, and merge that change to `main`. The key works only for pull requests whose base already has the entry, so the pull request that adds a key cannot itself be attested with it. Every entry needs an `expiresAt` in ISO-8601 UTC; the default is 30 days out and `--days` takes at most 90, which the verifier enforces too.
- **Revoking a key.** Remove its entry on `main`. That takes effect for events whose base commit no longer lists it: a pull request whose base still has the entry can still be attested with that key until the pull request is updated or re-based. Expiry is the backstop, so keep it short.
- **The evidence in a record is what was observed.** `environment.dockerEngine` is whether an engine answered when the run started; `environment.tools` holds the versions `node`, `pnpm` and `turbo` reported, and the engine's version only when one answered. A job whose tests start containers (`workspace_tests`) is not run or signed for when no engine answers, and the verifier refuses it from a record that says there was none. The PR impact gate's jobs then go together, so a run on a machine without an engine covers the other jobs only.
- **The environment a step gets.** Steps start from an allowlist of this machine's variables: `PATH`, locale and terminal, proxies and certificate paths, tool locations, `TURBO_*`, `MISE_*`, `TESTCONTAINERS_*`, and the CI-shaped variables the runner sets. Any name that says it holds a credential (`*TOKEN*`, `*SECRET*`, `*PASSWORD*`, `*AUTH*`, `*_PAT`, `*_KEY`, and the like) is dropped even under an allowed prefix, and so is every other variable; a step that needs one declares it in its own `env`, as in the workflow. `HOME` and `XDG_CONFIG_HOME` point at a scratch directory that is removed afterwards, so `~/.config/hobo/ci-attestor`, `~/.npmrc`, `~/.gitconfig`, `~/.ssh` and `~/.aws` are not where tools look. Caches keep working through explicit paths (`XDG_CACHE_HOME`, `XDG_DATA_HOME`, and Cargo, Rustup, Bun, mise and npm cache directories where they exist). `run` refuses a key file kept inside the checkout or one of those cache paths.

**Limits. Read these before relying on it.**

- **It does not strengthen the pull-request boundary, and does not weaken it.** A same-repository pull request can already edit the workflow it is tested by, including the verify step and the gate. This change adds no new way around that and closes none.
- **Reading keys at the base commit stops one thing:** a pull request adding its own key to `.hobo/ci-attestors.json` and signing with it. Nothing more.
- **Whoever holds an attestor's private key can make the covered checks pass without running them.** The record says what a machine claims it ran. Treat a key like merge rights on the covered checks: few entries, short expiry, removed when the machine goes away.
- **Never attest code you would not give the key to.** The commands under test run as the same user as the signing key. The allowlisted environment and scratch `HOME` keep a test from finding the key by accident; they do not stop code that looks for it, because same-user isolation is not a sandbox. Code from a pull request you have not read can read the key file by its absolute path and sign anything.
- **Changing a guard runs the guards.** A change to either workflow, the route action, the verifier, the job description, the trusted keys or the lint selects `pnpm run test:attestation` and `pnpm run actions:lint` in `agent:check` (`scripts/relevant-check-policy.ts`), which the PR impact validation runs. Affected lanes and workspace tests select nothing for such a change, because none of these files belongs to a package.
- **Container-backed tests are skipped where no Docker engine answers.** The runner asks the engine once, when the run starts, and records the answer in `environment.dockerEngine`. A record made without an engine did not run the container tests.
- **Turbo replays cached results, as it does in CI.** A task whose inputs are unchanged is not run again, and its cached result may come from a run with no Docker engine. So `dockerEngine: true` says an engine answered, not that every container test ran in this run. `pnpm ci:attest run --fresh` runs every task again.
- **Every trust entry expires.** An expired entry is refused even if the signature is good, and a list with an entry that reaches more than 90 days ahead is refused whole.
- **Not everything a CI machine has is reproduced.** Repository variables and secrets are empty locally, so there is no remote Turbo cache. Step and job timeouts are not enforced. The pinned headless browser is used if this machine already has it and is not downloaded.
- **The pull request's base in the event must be the base the run tested against.** If `main` moved after the run, the trees differ and CI runs normally. Merge `main` in and run again.
- **Anyone who can push to the repository can write to `ci-attestations`.** That lets them publish records, not forge one: an unsigned record, or one altered after it was signed, is refused whatever the branch holds.
- **Protect the audit trail.** The branch is the record of what was attested. Protect `ci-attestations` with a ruleset that blocks deletion and force-push, so a published record cannot be quietly removed or rewritten. This repository does not set that ruleset; an administrator has to.

**Where it lives:** `scripts/ci/attestation.mts` (format, signing, verification), `scripts/ci/verify-attestation.mts` (the route job's step), `scripts/ci/local-attest.mts` (`pnpm ci:attest`), `scripts/ci/attested-jobs.json` and `attested-jobs.mts` (what a local run executes), `.hobo/ci-attestors.json` (trusted public keys).

### 7. Merge queue (landing, not pickup)

**Merge queue** requires branch protection on `main` with merge queue enabled and the required HoBo CI checks. **Main full gate** is not one of them and does not run on `merge_group` (it runs on the push to `main`), so a queue entry holds no slot for it. Instead, the required **PR impact gate** runs on `merge_group` and executes Main full gate's affected S0 and dependent workspace-test lanes against the merge group's base SHA. That gates **merge** after jobs complete; it does not cause **`queued`** by itself. The required **CI fabric contract guard** runs only on `pull_request`; its two contract steps run inside **Main full gate** on push, schedule and dispatch, and inside **PR impact gate** on `merge_group`.

Set repository variables **`TURBO_TEAM`** and secret **`TURBO_TOKEN`** for remote Turbo cache (fork PRs use read-only remote mode in workflow).

Without them, a box job's Turbo local cache is **`hobo-turbo-cache`** inside the host-mounted pnpm store (`TURBO_CACHE_DIR`, set by `.github/actions/turbo-cache` when `HOBO_CI_PNPM_STORE_MOUNTED=1`). Same-repository PR, merge-group, push, dispatch and schedule jobs share it, so a main push replays the test tasks its PR already passed on the same tree. A PR whose head repository is not this one (a fork, or a deleted fork) never gets `TURBO_CACHE_DIR` and keeps the per-ref `actions/cache` fallback. `scripts/ci/turbo-cache-prune.mts` drops entries unused for 7 days (`HOBO_TURBO_CACHE_KEEP_DAYS`). Runners without the mount keep the per-ref `actions/cache` fallback. See [finding 12](../../docs/ci/findings/0012-main-re-ran-the-tests-its-own-pr-had-just-passed.md).

**Workspace hygiene on the box:** a deps-layer or aborted checkout can leave `packages/*` directories without a `package.json` (for example after `hobo-code` moved off `main`). HoBo CI Fabric runs `scripts/ci/prune-stray-workspace-packages.mts` before **S0** gates so `pnpm konsistent` does not treat those folders as broken packages.

## Follow a job from an agent (MCP)

An agent with an account token does not need to poll these endpoints. The
relay is an MCP server at `https://<relay-origin>/mcp` (`hobo ci serve`:
`http://127.0.0.1:8787/mcp`): `list_pending_jobs` shows what is queued without
a lease, `list_leases` and `get_lease` show where a lease is stuck, and
`wait_for_events` returns the moment a job is queued, reserved, claimed,
settled, cancelled or expired. `list_mesh_nodes` shows the runner nodes behind
the relay: which are live, their free capacity and how far each is trusted. Setup, the tool list and the client
configuration are in
[`packages/ci-gh-actions/README.md`](../ci-gh-actions/README.md#mcp-server).

## What repo CI cannot fix

These require org admin / platform operator action, not a workflow edit:

- Installing or re-pointing the GitHub App after org transfer.
- Relay deploy, secrets, the relay's cache, Vercel Sandbox credentials.
- Re-onboarding **Hobo-Labs/HoBo** in relay policy.
- Org/repo **Actions** permissions for fork PRs if you expect fork contributions to run CI.

Workflow YAML in this repository requests **`hobo`** or **`hobo-trunk`** unless the route job sent the run elsewhere; a permanently **`queued`** run on those labels means **no matching JIT runner registered**, almost always because the relay did not admit or launch the job.
