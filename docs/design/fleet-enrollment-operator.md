# Fleet enrollment operator guide

Operator semantics and limits from [`fleet-enrollment-design.md`](./fleet-enrollment-design.md), especially Sections 2.3, 6, and 17.4. The [scorecard](./fleet-enrollment-scorecard.md) is generated by `scripts/generate-fleet-enrollment-scorecard.mts`; do not hand-edit it — change the generator and regenerate.

**Implementation state (honest scope):** the transactional strict stores (SQLite + Postgres), state machines, and the fail-closed start authorizer are implemented and conformance-tested. The production GitHub assignment lookup and the controller endpoint that installs the pre-job hook are **not wired yet**, so no strict start can authorize in production today — authorization fails closed by construction. Kubernetes and Dagger paths are planner/boundary only. The [scorecard](./fleet-enrollment-scorecard.md) marks these rows `not-implemented`.

## Admission modes and execution guarantees

- **Standalone SQLite box mode** remains a single admission authority. Enrolling several workers does not turn it into a shared fleet.
- **Shared-fleet mode** requires one authoritative transactional store. Durable demands, runner slots, execution claims, capacity groups, effects, and worker fences share that store.
- **Strict, start-fenced execution** authorizes an actual job attempt at most once through the transactional claim and runner pre-job hook. It does not promise exactly-once user code.
- **External-assignment execution** has admission and reconciliation intent only. Hosted runners and ARC installations without a validated HoBo pre-start hook must not be labeled strict.

Trusted-local accepts only private, trusted, non-isolated jobs and is not a hostile-code sandbox. Isolated-required, public, or fork work needs an approved isolated profile. Never mix trusted-local and isolated-required Offers behind one `runs-on: hobo` label. Keep the workflow pool label independent of hostnames, cluster names, and provider IDs.

## Cluster join and multi-engine capacity

Joining a cluster starts with observation-only Connection state. An operator must explicitly bind CI capacity; join does not install ARC, Dagger, or unrelated controllers. Use namespaced least-privilege Roles, separate near-rightless job ServiceAccounts, and no cluster-admin kubeconfig. ARC is `start-fenced` only after its real runner template contains the HoBo hook and passes strict conformance; otherwise it is `external-assignment`. A scale set has exactly one owner: the central HoBo listener or ARC, never both.

A device's capacity group has an operator-approved fixed unit ceiling. Independently admitted GitHub and Dagger Offers draw from that same ceiling. Units are admission accounting, not guaranteed cores or GiB, and worker observations cannot raise the ceiling. Nested Dagger, BuildKit, Docker, or remote-builder calls inside a workflow are not reserved unless a future composite Offer can observe and fence them.

## Device operations

- **Pause:** deny new admissions and clean up unbound registered runners where possible.
- **Drain:** deny new admissions and wait for active work up to the configured bound.
- **Revoke:** invalidate enrollment and future credentials; stop realization best-effort while unresolved claims remain uncertain.
- **Quarantine:** deny new starts and effects pending reconciliation while retaining evidence.

None of these operations instantly terminates arbitrary code already running on a user-owned device.

## Restore, retry, and fail-closed starts

After every restore, mint a new controller incarnation, invalidate previous worker sessions and slot binding credentials, preserve claim tombstones, quarantine every provider scope whose post-backup state is not proven complete, and reconcile before resuming admission. Never expire all claims and reissue them.

A manual GitHub rerun is a new run attempt and may receive a new claim. User-authored retries, reusable workflows, and runners outside HoBo's runner group are not made idempotent by this design. Do not retry ambiguous provisioning, registration, start, cancellation, completion, or cleanup on another worker or engine.

If assignment verification, the transactional store, or the start-fence endpoint is unavailable, the pre-job hook fails closed. A job can therefore fail without running any workflow steps; this is intentional duplicate-start prevention, not proof that the job already ran.

## Status and residual limitations

Status and explain output distinguish controller readiness from supply readiness, observed demand from reserved capacity, runner registration from start authorization, fixed from elastic capacity, trusted from isolated execution, and strict from external-assignment guarantees. Queue and uncertainty reasons must remain visible.

External systems do not participate in HoBo's database transaction. A compromised control plane retains legitimate CI authority while compromised. A restored database cannot prove what providers did after the backup. Engine registration controls what HoBo may provision, not what workflow code can reach through ambient host or network access. These limits remain even when all local conformance tests pass; production readiness still requires the design's real deployment and authorized provider evidence.

## G9 live staging credentials (scorecard blockers)

The scorecard marks G9 live rows `blocked-on-credentials` until authorized staging evidence exists. Do not mark them `pass` from mocks, PACT doubles, or unit tests alone. Provision **test-only** credentials (never production Apps, repos, or ledgers):

| Credential | Purpose |
| --- | --- |
| **GitHub App ID** (`HOBO_FLEET_G9_GITHUB_APP_ID`) | Dedicated test App for staging acceptance |
| **GitHub App Installation ID** (`HOBO_FLEET_G9_GITHUB_APP_INSTALLATION_ID`) | Installation on the authorized test org |
| **GitHub App private key PEM** (`HOBO_FLEET_G9_GITHUB_APP_PRIVATE_KEY_PEM`) | Signs App JWTs for staging controller |
| **Authorized test repository IDs** (`HOBO_FLEET_G9_TEST_REPOSITORY_IDS`) | Private trusted + isolated-required workflow repos |
| **Staging transactional Postgres** (`HOBO_FLEET_G9_DATABASE_URL`) | Production-shaped strict v2 store (not local SQLite-only) |
| **Staging controller HTTPS origin** (`HOBO_FLEET_G9_CONTROLLER_BASE_URL`) | Stable origin for webhooks, hook, and repair |
| **Kubernetes / Station connection** (`HOBO_FLEET_G9_K8S_CONNECTION`) | Kubeconfig or Station/Yard Connection binding for strict runner-Pod jobs |
| **Operator Dagger engine** (`HOBO_FLEET_G9_DAGGER_ENGINE`) | Endpoint + auth for portable-pipeline acceptance |
| **Staging backup/restore access** (`HOBO_FLEET_G9_BACKUP_RESTORE`) | Operator credentials to run G9 drill #10 without duplicate execution |

Record deployment version, config digest, image digests, GitHub run/job IDs, cluster version, and artifact references when flipping these rows to `pass`. See design Section 18 G9 for the ten required live evidence items.
